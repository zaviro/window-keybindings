Window Keybindings

一套把窗口当作“有名字的对象”而不是“空间中的矩形”的键盘交互规范。先定义用户意图，再由 niri、Hyprland、Noctalia 或其他后端实现。

创建窗口是自由的；创建后可以遗忘。切换时只需要知道“我要什么”，不需要记住“它现在在哪里”。
没有匹配项。尝试换一个关键词或选择“全部”。

01 · 先记住五件事

这是整套规范的最小心智模型。只看这一节，也应该能理解后面的所有快捷键。

位置不是身份核心
窗口在哪里、先后创建顺序、MRU 距离，都不能成为识别窗口的必要条件。
规范：后台窗口的空间位置只是 compositor 的实现细节。

为什么

“浏览器在左边第三个”要求用户记住偶然状态；“browser”直接复用用户已有的语义记忆。

允许的例外

当两个窗口此刻同时可见时，左/右关系就在眼前，此时空间导航是合理的。

创建后可遗忘核心
创建窗口后，不要求 mark、重命名、移动到固定位置或记住工作区。

禁止把管理成本推给用户

传统 mark 会引入“命名 → 记忆 → 生命周期维护”的第二套知识。搜索应优先使用用户本来就知道的应用名、窗口标题、项目名。

理想状态：创建 → 使用 → 离开。未来需要时直接按名字或 role 找回。
已知目标直接寻址核心
知道“我要浏览器”时，不应通过方向键或反复 Tab 去寻找。

Mod+B 的意义不是少按几次键，而是消除“它在哪里”的认知步骤。

我要 Browser→ Mod+B→ 当前任务 browser 被激活 / 不存在则创建
长尾目标按名字搜索核心
不是每个应用都值得占一个字母；2–3 个字符的稳定搜索是兜底。

搜索对象应包括 role、具体窗口、named workspace、global-main 和未运行应用。

搜索排序必须稳定；状态不变时，同一查询不应随机改变第一候选。

空间只在“同时可见”时有意义核心
后台没有二维地图；前台 composition 才有左、右、上下和比例。

因此 niri 的横向 strip 并不天然违反本设计：只要隐藏列顺序不要求用户记忆即可。

布局系统要管理的是“当前可见组合”，不是永久保存整个 workspace 的二维地图。

02 · Workspace：有名字，数字只是别名

工作区代表任务上下文，而不是第几个容器。

Workspace 必须有语义名称核心
例如 main、window-keybindings、learning、media、game。
内部 ID、屏幕位置、当前排序不能成为 workspace 的身份。

匿名“workspace 4”仍要求用户额外记住“4 = 某项目”。名字本身已经足以表达对象。

Mod+1..9 是快速槽位暂定
数字保留肌肉记忆，但不承担永久身份。

建议 UI 显示 2: window-keybindings，而不是只显示 2。

忘记数字映射时，始终可以通过名称搜索进入同一 workspace。

待定slot 是固定类别（main/project/media），还是用户动态绑定 named workspace？
搜索是数字槽位的兜底核心
Mod+Space → “win” → window-keybindings。

因此不需要给每个 workspace 建 mark，也不强迫所有任务挤进 1..9。

顺序遍历降级为辅助暂定
Mod+PageUp/PageDown 只用于“附近那个工作区”。

沿用 niri 的成熟习惯，但不能要求用户用顺序来记工作区身份。

03 · Role：用户意图，不是应用名

Browser、Terminal、Editor、Agent 是稳定语义；Firefox、Ghostty、Zed 只是当前实现。

Local role键位暂定
Mod+B browser · Mod+T terminal · Mod+E editor · Mod+A agent

语义

“当前任务中，我要这个角色。”

确定性行为

  1. 当前 workspace 已绑定该 local role → 激活；
  2. 没有绑定，但存在可认领匹配窗口 → 按确定性规则认领并激活；
  3. 完全没有 → 创建并绑定。

额外同类窗口仍可以自由创建，但只是 ordinary windows，不应让 role 目标每次随 MRU 漂移。

Global Main role键位暂定
Mod+Alt+B 表示“全局主浏览器”，Alt 统一表达 scope 提升。
Mod窗口系统层
Altlocal → global-main
Shift呈现/结构变体
Ctrlmove/send

关键规则：拉窗口，不拉用户

global-main 已存在时，将它召回当前 workspace 并聚焦；不存在则在当前 workspace 创建。默认禁止跳去它原来的 workspace。

这样用户不需要记住“我刚才从哪里来”。

Global Main 是可漫游对象核心
它没有必须返回的 home workspace；物理位置不属于身份。

如果 A、B 两个 workspace 都需要同时存在 browser，应各自拥有 local browser；global-main 的职责是“唯一可召回主对象”。

多实例与认领规则未解决
同一 workspace 已有三个 Firefox 时，哪个成为 local browser？

当前约束只有两条：

  1. role slot 一旦绑定，在窗口存活期间保持稳定；
  2. 不能每次偷偷选不同 MRU 窗口。
需要人工验证自动认领候选的最终确定性规则尚未定案。

04 · Search：统一对象寻址

搜索不是传统“应用启动器”，而是 window / role / workspace / app 的统一入口。

Mod+Space · switch-or-create暂定
优先去已有对象；不存在时才启动。

候选可以同时出现

Firefox — GitHub [window · current]Firefox — YouTube [window · workspace:media]window-keybindings [workspace]browser [role · local]Firefox [application · new]

建议排序

  1. 当前 workspace 精确 role / alias；
  2. 当前 workspace 窗口；
  3. named workspace；
  4. global-main；
  5. 其他 workspace 运行窗口；
  6. 未运行应用。
Mod+D · force-new暂定
明确表达“我要再开一个”，与导航彻底分离。

沿用 niri 默认 Mod+D “Run an Application”的语义基础，但将其收窄为 deliberate create。

对于单实例应用，force-new 至少请求新窗口；最终是否产生独立进程由应用决定。

待定Noctalia 现有 launcher UI 如何清楚区分“切换/复用”和“明确新建”？
Mod+Tab · 只负责“回到刚才”核心语义
时间历史不是通用搜索，也不承担“我要 Firefox”。

Alt+Tab 可以保留为传统兼容别名 / Noctalia window switcher。

长期目标：历史甚至可以恢复之前的可见 composition，而不仅是焦点窗口。

05 · Layout：管理当前可见组合，不管理后台地图

“去 Browser”和“保留 Editor 并把 Browser 放旁边”是两个不同用户意图。

Plain activation关键未决
Mod+B 的呈现结果到底应该多强？

已确定的语义只有：“现在主要看 browser”。

如果 browser 已经在当前可见 composition 中，应只聚焦，不做无意义重排。

尚未定案目标在后台时，是否总是变成 solo/maximized？还是保留已有 composition？
尚未定案已有 50/50 split 时，plain activation 是 focus、替换 pane，还是 collapse 为 solo？
Compose activation语法暂定
Shift = “保留当前对象，并把目标加入可见区域”。
Mod+B → local + plainMod+Alt+B → global + plainMod+Shift+B → local + composeMod+Alt+Shift+B → global + compose

优势是 modifier 正交：Alt 只改变作用域，Shift 只改变呈现方式。

默认二分屏暂定
Compose 默认 50/50，目标放右侧。
[ Current ][ Target ]

理由：当前对象通常是主上下文，新对象多为浏览器、终端、参考资料；固定默认比每次询问方向快。

待定右侧是否足够自然？是否需要 one-shot placement mode 表达 left/right/up/down？
方向键只控制可见邻居暂定
Mod+方向 切换可见 pane；不负责寻找屏幕外后台窗口。

当空间关系就在眼前时，“去左边”无需记忆；当窗口隐藏在后台时，应该按名字或 role 寻址。

这也是 niri 实现时最明显需要适配的地方：默认方向导航会继续滚向屏幕外列。

结构操作进入专用层暂定
Mod+Shift+方向 重排；Mod+R 进入 resize mode。

低频结构操作适合 mode；高频导航不应该进入 mode。

Mod+R → resize mode方向键 → 调整边界Enter / Esc → 退出
显示状态暂定
Mod+F solo/maximize · Mod+Shift+F true fullscreen · Mod+V floating

区分工作模式的 maximize/solo 与真正占满输出的 fullscreen。F = Fill/Fullscreen，V 延续 niri/Hyprland 常见 floating toggle 习惯。

06 · 快捷键语法

目标不是背几十个组合，而是先学 modifier 语法，再自然推导具体动作。

Mod窗口 / compositor 系统层
Alt把 local 作用域提升为 global-main
Shift呈现/结构变体：compose、move
Ctrl把当前对象 send/move 到目标

其中 Ctrl 语义直接借鉴 niri 默认体系中“导航键 + Ctrl = 移动当前窗口/列到那里”的一致设计。

快捷键暂定语义为什么选它
Mod+Space统一对象搜索，switch-or-createNoctalia launcher 习惯；Space 易按，适合最高频入口
Mod+D搜索并明确 force-new继承 niri “Run Application”语义，并消除切换/新建歧义
Mod+Blocal browserB = Browser
Mod+Tlocal terminalT = Terminal；继承 niri 默认终端键
Mod+Elocal editorE = Editor；但与 Explorer/File Manager 习惯存在冲突，待验证
Mod+Alocal agentA = Agent
Mod+Alt+角色键对应 global-main roleAlt 统一表示 global scope
Mod+Shift+角色键保留当前窗口并 compose 目标Shift 统一表示结构/呈现变体
Mod+Tabprevious/recent成熟的时间导航语义；只回答“回到刚才”
Mod+1..9named workspace 的快速槽位成熟肌肉记忆，但数字不作为身份
Mod+Ctrl+1..9send 当前窗口到槽位Ctrl 延续 niri 的 move/send 语法
Mod+PageUp/Down相邻 workspace沿用 niri；仅辅助，不承担身份记忆
Mod+方向当前可见 composition 内切换 pane空间关系此刻可见，认知成本低
Mod+Shift+方向重排当前可见 paneShift = 结构变体
Mod+Rresize modeR = Resize；niri/Hyprland 都有尺寸调整先例
Mod+Fsolo / maximizeF = Fill
Mod+Shift+Ftrue fullscreen继承 niri 默认语义
Mod+Vfloating toggle延续 niri/Hyprland 常见习惯
Mod+Q关闭当前窗口Q = Quit；niri 默认

07 · 后端适配：规范不属于某个 WM

后端只负责把同一用户语义翻译成各自机制。

niri语义层足够
后台 strip 可以退化成实现细节；真正需要适配的是 composition。

已有 named workspace、窗口/工作区 JSON IPC、按 ID focus、move-to-workspace、recent windows、floating/fullscreen/maximize 等能力。

主要摩擦：默认 Mod+方向 会沿无限 strip 找到屏幕外窗口；二维 split/composition 需要组合列、同列窗口和尺寸动作。

Hyprland完整实验后端
named/special workspace、focuswindow、tags/rules、master、submap 更天然承载布局语义。

更适合 explicit split、master/secondary composition、resize mode、one-shot placement 和 global-main summon。

但不能反过来要求用户记住 Hyprland 的后台布局树；规范仍然以语义对象为第一层。

Noctalia交互前端
适合承担 launcher/search、window switcher、workspace/role 状态展示。

真正的 focus、move、spawn、role registry、composition 应由 compositor/helper 层完成。

当前规范保留 Mod+Space launcher/search 和 Alt+Tab 传统 switcher 的成熟语义。

08 · 实现前必须讨论

这些不是缺失文档，而是故意不提前定死的设计决策。

Plain activation 的布局结果高优先级
focus、替换 pane、还是 collapse 到 solo？
  1. 目标已可见：基本确定只 focus。
  2. 目标在后台：是否成为主视图尚未确定。
  3. 已有 split：是否保持 composition 尚未确定。
Compose 的方向语法高优先级
默认右侧 50/50 是否足够？如何表达 left/up/down？

直接使用两个非 modifier 键（如 Left+B）对 niri/Hyprland 都不自然，可能需要 one-shot placement mode / leader。

Mod+E 是否应属于 Editor待验证
E=Editor 很直接，但不少桌面把 E 理解为 Explorer/File Manager。

应通过实际使用验证肌肉记忆冲突，而不是仅凭字母助记定案。

Mod+D 的新建 UI待验证
如何让用户明确知道这是 force-new，而不是普通 launcher？

需要与 Noctalia 的搜索 UI 一起设计。

Workspace slot 策略待定
1..9 是固定类别，还是动态绑定 named workspace？

目标是兼顾肌肉记忆与语义名称，不能退化成匿名编号。

多显示器模型待定
named workspace 全局唯一还是 output-local？global-main 如何跨屏召回？

需要先确定“任务上下文”和“物理输出”谁拥有更高层级。

Global Main 是 move 还是 clone/new待定
某些场景是否不应从另一个 workspace 抢走主实例？

当前草案默认 move，因为 global-main 是可漫游唯一对象；如需要并存，应优先使用 local role。

History 是否恢复 composition长期
Mod+Tab 是否只回窗口，还是回完整 view state？

恢复 composition 更符合“回到刚才”，但实现复杂度明显更高，因此当前是 SHOULD 而非 MUST。

Local role 自动认领待定
多个匹配窗口时需要可预测且稳定的确定性规则。

不能让 role 每次随 MRU 漂移；普通搜索则可以列出全部窗口让用户选择。

搜索前缀是否需要低优先级
是否提供 window:/ws:/app: 等可选限定，但默认无需输入？

默认路径应保持 2–3 字符 + Enter；前缀只能作为消歧增强，不能成为日常负担。

09 · 新设计的检查清单

以后每加入一个快捷键或行为，都先过这七个问题。

  1. 用户已经知道目标对象吗？如果知道，为什么还要搜索位置？
  2. 这个动作是否要求用户记住窗口的偶然状态？
  3. 创建后是否产生新的维护义务？
  4. 相同 modifier 在其他键上是否保持同一语义？
  5. 操作结束后，用户是否还需要记住“我从哪里来”？
  6. 这个行为是在表达用户意图，还是暴露 compositor 内部数据结构？
  7. 如果换掉 niri / Hyprland，这个快捷键的用户意义还能保持吗？

这是讨论用 Draft，而不是实现约束。完整原始文本仍保留在 SPEC.md，来源与现有生态对照保留在 REFERENCES.md。
