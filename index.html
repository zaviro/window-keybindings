1

Role：只保留真正高频对象

B / T 进入核心；E / A 只保留名字，不占键位
Mod+B暂定
当前 workspace browser：已有则 focus，没有则创建并绑定为 local browser。
Mod+T暂定
当前 workspace terminal：沿用 niri 官方 T=Terminal，但把默认 spawn 语义升级为 focus-or-create。
Mod+Alt+B暂定
global-main browser：存在于别处就拉到当前 workspace；不存在才创建。
Mod+Alt+T待验证
global-main terminal：逻辑同上，但是否值得长期占键仍需实际体验。
Mod+E保留不绑定
Editor role 名称保留。编辑器生态和实际主编辑对象尚不稳定，暂不建立肌肉记忆。
Mod+A保留不绑定
AI / Assistant role 名称保留。只有未来出现明确、高频、稳定的 AI 对象时再启用。
原则：固定键不是应用收藏夹。只有达到“我经常明确想去这个对象”的稳定 role 才值得占一个字母。
2

搜索：只保留 Mod+D

复用 Noctalia，不再同时维护 Mod+Space

目标

Mod+D 打开统一 Destination Search。输入通常 2–3 个字符，结果可以同时包含运行中窗口、应用和 named workspace。

Chrome — GitHub window → 跳转已有窗口
Google Chrome application → 启动应用/新窗口
window-keybindings workspace → 跳转工作区

为什么复用 Noctalia

Noctalia 已有 applications 与 windows provider；先把 windows provider 纳入普通搜索并验证 ranking。只有实际体验不足时，才写薄 provider/plugin，不另造完整 launcher。

已删除

Mod+Space → 第二个统一搜索入口

原因：和 Mod+D 重叠，同时更容易撞到应用、输入法或桌面快捷键。

3

Workspace：名字是身份，数字是别名

忘掉编号也能通过名字回来

长期 workspace 使用名字，例如 main、window-keybindings、learning。内部顺序、workspace ID 和显示器位置都不构成身份。

Mod+1..9
保留为稳定快速槽位，例如 2 → window-keybindings。
Mod+D → win
忘记数字后按名称搜索恢复，不产生“匿名 workspace 4 是什么”的负担。

自动命名属于后续 policy：niri 原生负责 named workspace / 按名 focus；helper 可以根据项目或事件流决定名称。

5

删除：Shift+Role = Compose

分屏属于布局层，不绑死到 role 层

Mod+Shift+B → 保留当前窗口并把 Browser 放旁边

这个语义不够直觉，而且会和 niri 原生大量 Shift 结构操作混淆。用户产生疑惑本身就是信号：不应继续固化。

分屏、组合、placement 后续单独讨论，优先复用 niri / Hyprland 的布局能力。

6

实现：niri 默认不是 focus-or-create

role 需要一个很薄的 IPC helper

niri 官方默认 Mod+T 的动作是 spawn。它不会先查找已有窗口。

key → helper → query windows → match ? focus-window : spawn

global-main 在此基础上再增加 move-window-to-workspace。这些都是 niri IPC 已提供的原子能力，因此无需修改 compositor。

7

下一轮只验证这些问题

避免继续在纸面上增加功能
  1. Noctalia 的 windows + applications 搜索排序是否已经足够自然？
  2. Mod+B/Mod+T focus-or-create 是否真的比纯 spawn 更顺手？
  3. 多个 Browser 窗口存在时，local browser role 应怎样稳定绑定？
  4. Mod+Alt+T 是否真的值得存在？
  5. named workspace 是否需要自动命名，还是搜索+手动命名已经足够？
  6. 分屏是否完全交给 niri 原生操作就够了？只有体验不足时再设计 placement 语义。
  7. 什么时候 Editor / AI role 达到值得启用固定键的频率？
